# Занятие 6: архитектура и основы DDD

Один заказ постепенно проходит путь от жирного HTTP-handler до приложения с отдельными сценариями, предметными правилами и адаптерами. Go 1.22+. Итог по умолчанию работает в памяти, без Docker и внешнего сервиса; первый запуск скачивает pgx, необходимый для необязательного PostgreSQL.

## Запуск

```sh
cd ~/code/go-courses/lecture6_architecture
go mod download
go run ./cmd
```

В другом терминале:

```sh
curl -i http://127.0.0.1:8086/orders \
  -H 'Content-Type: application/json' \
  -d '{"items":[{"product_id":42,"quantity":2},{"product_id":17,"quantity":1}]}'
```

Ответ: HTTP 201, `{"order_id":1}`. Две позиции стоят 39900 копеек. Каталог: товар 42 — 15000 копеек, товар 17 — 9900 копеек. Следующие заказы в том же процессе получают следующие ID. При перезапуске данные памяти исчезают.

Тот же сценарий из другого входа:

```sh
go run ./cmd -mode cli -product 42 -quantity 2
```

CLI создаёт собственный процесс и собственное хранилище, поэтому ID снова начинается с 1. Это вызов того же `usecase.Service.CreateOrder`, без HTTP. В презентации второй транспорт показан как gRPC; в запускаемом примере выбран CLI, чтобы показать повторное использование без генерации protobuf. Полный gRPC-пример курса находится в соседней `lecture5_grpc`.

## Что открывать по блокам

| Блок лекции | Файлы | Смысл |
| --- | --- | --- |
| 1. Всё внутри handler | `stages/01_handler/handler.go` | HTTP, проверки, расчёт и SQL вместе |
| 2. Выделяем сценарий | `stages/02_usecase/service.go`, `internal/dto/create_order.go` | Операция оформления не зависит от HTTP |
| 3. Domain | `stages/03_domain/service.go`, `internal/domain/order.go` | Порядок действий отдельно от правил заказа |
| 4. Адаптеры | `stages/04_adapters/service.go`, `internal/adapter/postgres.go` | SQL уходит, конкретная зависимость остаётся |
| 5. Интерфейсы | `internal/usecase/service.go`, `service_test.go` | Контракты потребителя и тест без БД |
| 6. Сборка и пакеты | `cmd/main.go`, `internal/controller/http.go` | Реализации выбирает точка сборки |
| 7. Сравнение архитектур | Структура и импорты итогового `internal/` | Layered, ports/adapters, dependency rule |

`stages/` — компилируемые снимки промежуточных состояний для чтения и сравнения, не отдельные серверы. Они намеренно сохраняют недостатки своего этапа; запускать следует итоговый `cmd`. В слайдах код сокращён до читаемых фрагментов; здесь показаны полные реализации. Не все детали итогового кода помещаются на слайдах: ограничение тела HTTP-запроса, проверка лишнего JSON, отмена контекста, обработка переполнения и graceful shutdown.

## PostgreSQL вместо памяти

```sh
docker compose up -d
DATABASE_URL='postgres://lecture:lecture@localhost:5436/orders?sslmode=disable' go run ./cmd
```

Схема и две цены создаются через `schema.sql` при первом запуске контейнера. Сохранение заказа — один INSERT, items хранятся в JSONB с ценами на момент оформления. Для просмотра:

```sh
docker compose exec postgres psql -U lecture -d orders -c 'SELECT * FROM orders;'
docker compose down
```

Пример не резервирует товары и не проводит платежи. Между чтением цен и сохранением нет общей транзакции: для лекции принимаем, что каталог не меняется во время оформления. В реальной системе требуется договориться о политике цены, конкурентных изменениях и идемпотентности. Проверка количества сейчас происходит в `NewOrder` после чтения цен: если товар отсутствует и количество неверно одновременно, первой вернётся ошибка каталога.

## Проверка

```sh
make check
```

Проверяются предметные ограничения, переполнение суммы и защита модели от внешнего изменения, координация сценария, отсутствие сохранения при ошибке, передача контекста и граница HTTP. PostgreSQL-адаптер компилируется, но unit-тесты не требуют работающей БД. Его запросы можно проверить вручную с контейнером по инструкции выше.

## Итоговая структура

```text
cmd/main.go             конфигурация, выбор адаптеров, запуск
internal/controller/    HTTP → DTO → сценарий → HTTP
internal/usecase/       сценарий и нужные ему интерфейсы
internal/domain/        заказ и его правила
internal/dto/           вход и результат сценария
internal/adapter/       память и PostgreSQL
internal/config/        чтение конфигурации
stages/                 промежуточные состояния
```

Repository — роль доступа к сохранённым предметным объектам. В этом примере `OrderRepository` сохраняет заказ, а `Catalog` получает цену. Не каждый внешний адаптер — repository. `adapter` и `usecase` связаны контрактами, но `usecase` не импортирует реализации; `cmd` импортирует обе стороны и соединяет их. Дерево папок само по себе не гарантирует правильное направление зависимостей.
