### Kafka: разделение на два сервиса

Нужно разделить приложение на два сервиса:

- `catalog-service` — общается с пользователем, хранит фильмы в PostgreSQL, использует Redis для поиска и кэша.
- `downloader-service` — скачивает фильмы с внешнего фильм-стенда.

Сервисы должны общаться асинхронно через Kafka.

Топики:

- `movie_download_tasks` — задачи на скачивание фильмов.
- `movie_downloaded` — скачанные фильмы.

Как это работает:

1. `catalog-service` на старте смотрит максимальный id фильма в PostgreSQL.
2. `catalog-service` отправляет в Kafka задачу `NeedToDownload` с этим id.
3. `downloader-service` читает задачу и скачивает со стенда все фильмы от `id + 1` до последнего доступного.
4. Каждый скачанный фильм `downloader-service` отправляет в Kafka.
5. `catalog-service` читает скачанные фильмы из Kafka и сохраняет их в PostgreSQL.

HTTP/gRPC API для пользователя остаётся в `catalog-service`.

### Конфигурация

Сервисы должны читать конфигурацию из переменных окружения:

- `MOVIE_BASE_URL` — базовый URL внешнего фильм-стенда, используется `downloader-service`;
- `HTTP_ADDR` — адрес HTTP-сервера, используется `catalog-service`;
- `DATABASE_URL` — строка подключения (DSN) к PostgreSQL;
- `REDIS_ADDR` — адрес Redis в формате `host:port`;
- `KAFKA_BROKERS` — адреса брокеров Kafka, перечисленные через запятую.

Сохраняются требования предыдущих ДЗ к приоритету значений из окружения, значениям по умолчанию для `MOVIE_BASE_URL` и `HTTP_ADDR` и запуску без обязательных CLI-аргументов.

Повторная обработка одного и того же фильма не должна создавать дубликаты в БД. Offset сообщения со скачанным фильмом должен коммититься только после успешной записи в PostgreSQL.

Для временных ошибок нужно сделать retry. Сообщения, которые не удалось обработать после нескольких попыток, должны попадать в DLQ.

Оба сервиса должны быть спроектированы по принципам чистой архитектуры из предыдущего ДЗ.
