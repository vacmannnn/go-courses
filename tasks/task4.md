### Архитектурный рефакторинг

В этом ДЗ нужно переписать сервис из ДЗ 3, применив архитектурный подход с лекции. Функциональность сервиса не должна измениться: HTTP и gRPC ручки из прошлого задания должны продолжить работать так же, как раньше.

Код нужно разделить минимум на следующие слои:

- `domain` — доменные модели и ошибки: `Movie`, ошибки валидации, ошибки отсутствующего фильма и т.д.
- `usecase` — бизнес-логика приложения: загрузка диапазона фильмов, поиск последнего фильма, валидация входных параметров.
- `adapter` — работа с внешними системами: клиент к фильм-стенду `GET /{id}/info.0.json`, преобразование внешнего JSON в доменную модель.
- `handler` — транспортный слой: HTTP handlers, gRPC server, преобразование HTTP/gRPC request/response в вызовы usecase.
- `cmd` — точки входа приложения: запуск HTTP/gRPC сервера, чтение конфигурации, сборка зависимостей.

Основное правило: бизнес-логика не должна зависеть от HTTP, gRPC или конкретного клиента к внешнему сайту. `usecase` должен работать через интерфейсы, а конкретные реализации должны подключаться в `cmd`.

Минимальные интерфейсы, которые нужно выделить:

```go
type MovieProvider interface {
    GetMovie(ctx context.Context, id int) (Movie, error)
}

type MovieUseCase interface {
    LoadMovies(ctx context.Context, from, to int) ([]Movie, error)
    GetLastMovie(ctx context.Context) (Movie, error)
}
```

Названия интерфейсов могут отличаться, если смысл остаётся тем же.

### Критерии оценивания

6 баллов — Код строго разделён на указанные слои. Все зависимости направлены внутрь (интерфейсы определены в usecase/domain, реализации в adapter). Использован Dependency Injection через конструкторы. Бизнес-логика полностью изолирована, тестируема (можно подменить адаптеры).

5 баллов — Архитектура соблюдена, но есть мелкие нарушения: например, usecase импортирует adapter напрямую (а не через интерфейс), или конфигурация читается внутри handler. Функциональность полностью сохранена.

4 балла — Слои выделены, но зависимости не до конца инвертированы (есть цикличность или жёсткая связность). При этом код работает. Или отсутствует cmd с явной сборкой.

3 балла — Разделение есть, но не на все слои (например, adapter смешан с handler), или бизнес-логика содержит HTTP-специфичные типы (нарушение). Работает, но рефакторинг неполный.

0–2 балла — Рефакторинг не выполнен или код не работает. Архитектура декларирована, но фактически осталась монолитной. Структура не соблюдена, бизнес-логика жёстко привязана к HTTP/gRPC.

Отметка за задание снижается при более поздней сдаче задания (1 балл за каждые 2 недели опоздания).
