# Go Courses

Материалы курса и задания — в [`tasks/`](tasks/). Общие преподавательские тесты —
в [`autotests/`](autotests/). Сейчас доступны ДЗ 1, ДЗ 2 и пять HTTP-тестов для ДЗ 3.
Результат проверки: прошли/не прошли, с деталями по каждому тесту.

## Как забурмалдить автопроверку

### Преподавателю — один раз

Опубликуйте изменения в основной ветке `main` репозитория `vacmannnn/go-courses`.
Тесты и `.github/workflows/grade.yml` должны быть доступны на GitHub.
Отдельный репозиторий тестов и ручной запуск проверки не нужны.

### Студенту — один раз

Скопируйте [`ci-example.yml`](ci-example.yml) из корня этого репозитория
в `.github/workflows/course.yml` **своего** репозитория и запушьте его.
Файл целиком, никаких параметров задания и путей менять не нужно:

```yaml
name: Homework
on: [pull_request, workflow_dispatch]
permissions:
  contents: read
jobs:
  homework:
    uses: vacmannnn/go-courses/.github/workflows/grade.yml@main
```

### На каждом ДЗ

1. Создайте ветку `task1`, `task2`, `task3` и т.д. (также подходят `task-3`, `task_3`, `feature/task3`).
2. Пушьте решение в свой репозиторий и откройте PR.
3. Смотрите результат **в Checks своего PR**. При обновлении PR тесты запускаются заново.

CI сам определяет номер ДЗ по имени ветки, находит `go.mod` и пакет `main`,
скачивает преподавательские тесты и запускает нужный набор. На следующем ДЗ
CI-файл остаётся тем же. Чтобы он был и в новых ветках, добавьте его в `main` своего репозитория.

### Какая структура решения подходит

Автоматически поддерживаются, например:

```text
# Вариант 1: актуальное решение в корне
student-repo/
├── go.mod
└── main.go

# Вариант 2: точка входа в cmd/server
student-repo/
├── go.mod
└── cmd/server/main.go

# Вариант 3: отдельные модули для разных ДЗ
student-repo/
├── task1/go.mod + main.go
├── task2/go.mod + main.go
└── task3/go.mod + cmd/server/main.go
```

В третьем варианте ветка `task3` выбирает модуль `task3`, предыдущие ДЗ не мешают.
Для других названий папок модуль тоже находится, если он единственный.
Если подходящих модулей или пакетов `main` несколько, CI выдаёт понятную ошибку со списком,
а не выбирает случайное решение. Build tags учитываются через `go list`.

Если номер ДЗ не найден в имени ветки, CI объяснит, как её назвать.
Пока есть тесты только для ДЗ 1–3; ветка `task4` выдаст сообщение, что набор ещё не реализован.

### Договор запуска приложения

Это настройка самого приложения, её достаточно поддержать один раз:

- ДЗ 1: `twoSum(nums []int, target int) []int` в `package main`.
- ДЗ 2: читать `MOVIE_BASE_URL` — базовый URL фильм-стенда.
- ДЗ 3: читать `MOVIE_BASE_URL` и `HTTP_ADDR` — адрес HTTP-сервера.

При обычном запуске можно использовать значения по умолчанию `https://homeworksite.site`
и `:8080`. В тестах приложение должно использовать переданные значения.
ДЗ 3 запускается без обязательных CLI-аргументов. Подробный контракт —
в [`autotests/README.md`](autotests/README.md).

### Версии и дополнительные способы запуска

В примере используется `@main`: новые тесты преподавателя подтягиваются автоматически.
Для фиксации условий потока можно один раз указать опубликованный тег или SHA
в ссылке workflow и такой же `tests-ref` в `with`. На каждом ДЗ менять это не нужно.

Для ручного запуска студент выбирает свою ветку `taskN` в **Actions → Homework → Run workflow**.
Также сохранён необязательный преподавательский запуск **Course acceptance tests**:
можно указать публичный репозиторий, PR ref вроде `refs/pull/2/head` и номер ДЗ;
пути по умолчанию определяются автоматически. Он не требуется для Checks у студентов.

## Локальный запуск

Нужны Go 1.26.4+, Python 3.9+ и Git (macOS/Linux).

```bash
cd ~/code/go-courses/autotests

# ДЗ 3, main лежит в cmd/server:
./scripts/check.sh task3 ~/code/student-homework/task3 --package cmd/server --report reports/task3.json

# Полностью автоматический выбор ДЗ и путей:
python3 scripts/ci.py --repo ~/code/student-homework --branch task3

# Демонстрация на тестовом HTTP-сервисе:
./scripts/check.sh task3 ./testdata/task3-good

# Проверка самого инструмента на рабочих и намеренно сломанных решениях:
make check
make test
```

Набор работает во временной копии решения. Это не sandbox: для неизвестного кода используйте
одноразовое окружение без секретов. В GitHub workflow используются GitHub-hosted runners
с правами только на чтение и без сохранения checkout credentials.

## Что покрыто

- ДЗ 1: Two Sum, краевые случаи и допустимость индексов.
- ДЗ 2: CLI, диапазон, параллельность и лимит воркеров, ошибки стенда, timeout, SIGINT.
- ДЗ 3: загрузка диапазона, невалидные параметры, последний фильм, Swagger, ошибка стенда.

gRPC и остальные критерии ДЗ 3 пока не покрыты. Зелёная проверка не заменяет ревью архитектуры,
оформления PR и остальных требований. Планы для ДЗ 4–10 — в [`autotests/ROADMAP.md`](autotests/ROADMAP.md).
